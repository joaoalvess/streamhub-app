**Dificuldade:** L · **Relevância:** crítica

## Abordagem proposta

O nome da feature ("P5/P8/P7 single-layer") é quase literalmente a joia da coroa citada pelo dono do projeto ("MKV com Dolby Vision nativo via remux HLS local → AVPlayer"). Isso não é coincidência: a única forma de obter Dolby Vision *de verdade* (o algoritmo proprietário de tone-mapping dinâmico por cena/frame que a Dolby licencia à Apple) num app tvOS é deixar o **VideoToolbox/AVFoundation nativos** decodificarem e aplicarem o RPU — nenhum player open source (mpv, VLC, Jellyfin/Swiftfin) reimplementa esse algoritmo; todos, na melhor das hipóteses, usam o RPU só como fonte de estatísticas (L1/L6, "ST2086-like") para alimentar o **próprio** tone-mapping genérico (BT.2446a/spline/Reinhard) quando fazem HDR→SDR/HDR10. Isso está confirmado tanto pela documentação do `libplacebo`/mpv ("Dolby Vision RPU for ST2086 metadata... default true when tonemapping from Dolby Vision") quanto pelo fato de que perfil 7 (dual-layer) é tratado como fallback genérico até no mpv mais recente. Reimplementar isso do zero no shader Metal do KSPlayer seria trabalho de XL (motor de tone-mapping dinâmico próprio) para produzir, na melhor das hipóteses, uma aproximação inferior ao que a própria Apple já faz de graça via passthrough — não vale o caminho crítico do StreamHub.

Proposta em duas fases:

### Fase 1 (a que entrega "Dolby Vision nativo" de verdade): passthrough via AVPlayer

Depende inteiramente do pipeline "MKV → HLS local (fMP4/CMAF) → `AVURLAsset`/`KSAVPlayer`" descrito em `context/investigation/proavplayer-mkv-com-dolby-vision-e-atmos-nativos-via-avplaye.md` (status **Ausente** — nenhum remuxer, servidor local ou mapeamento de metadata DV/Atmos existe hoje). Este roadmap não repete o design daquele subsistema (é feature própria, maior, provavelmente XL); documenta aqui apenas o que a fatia "dynamic metadata P5/P8/P7" exige dele:

1. **Preservar a config record DV no remux (stream copy, sem reencode)**: o fork já parseia o box `dvcC`/`dvvC` de entrada inteiro para `DOVIDecoderConfigurationRecord` (`FFmpegAssetTrack.swift:180`, via side data `AV_PKT_DATA_DOVI_CONF`) — e esse struct Swift é layout-compatível com o `AVDOVIDecoderConfigurationRecord` do libavutil (`dv_version_major/minor`, `dv_profile`, `dv_level`, `rpu_present_flag`, `el_present_flag`, `bl_present_flag`, `dv_bl_signal_compatibility_id`), ou seja, **todos os bytes necessários para remontar o box `dvcC`/`dvvC` de saída já estão em mãos**, só falta serializá-los de volta no formato ISOBMFF (24 bits fixos + reserved) e anexá-los ao `CMFormatDescription`/aos segmentos HLS de saída. Hoje isso não acontece: `FFmpegAssetTrack.swift:228-229` só grava o atom `hvcC` (`kCMFormatDescriptionExtension_SampleDescriptionExtensionAtoms`), nunca `dvcC`/`dvvC`; `CMVideoCodecType.avc` (`VideoToolboxDecode.swift:202-216`) só mapeia HEVC→`hvcC`, sem noção de Dolby Vision.
2. **RPU passthrough para P5 e P8 (já single-layer)**: nenhuma transformação é necessária além de manter o NAL unit type 62 (RPU) intacto durante o remux stream-copy — o `AVDOVIMetadata`/RPU já trafega no bitstream HEVC copiado 1:1 pelo `startRecord`/mux existente em `MEPlayerItem.swift:271-326` (ver `context/investigation/record-video.md`, status Presente — infraestrutura de remux pacote-a-pacote sem reencode já provada em produção pelo demo, é a base a estender para um muxer HLS/fMP4 em vez de `.mov`).
3. **Conversão P7 → single-layer (a parte "single-layer" do nome da feature)**: perfil 7 é dual-layer (BL+EL+RPU, MEL ou FEL) e **nenhum dispositivo Apple decodifica dual-layer nativamente** — confirmado por múltiplas fontes (AVS Forum: "Apple devices don't understand dual layer Dolby Vision formats"; mpv issues: "profile 7 with enhancement layers is not supported, falls back to generic HDR"). A única forma prática de reproduzir P7 nativamente num Apple TV é descartar a EL e reescrever o RPU como perfil 8.1 durante o remux — exatamente o que a comunidade faz hoje via `dovi_tool convert --discard -m 2` (mode 2, MIT license, `quietvoid/dovi_tool`). Como `dovi_tool` é um binário Rust e tvOS não permite `exec` de processos arbitrários, as opções reais são: (a) portar a lógica de conversão de modo 2 (mapear `dv_profile 7 → 8`, ajustar `dv_bl_signal_compatibility_id`, remover blocos de EL do RPU) para Swift/C usando as próprias structs já expostas pelo FFmpeg (`av_dovi_get_header/mapping/color`, já chamadas e descartadas em `FFmpegDecode.swift:98-100`); ou (b) vendorizar o crate Rust `dolby_vision` (também publicado como lib C-compatível, `libdovi`) como `staticlib` para `arm64-apple-tvos`/`ios` e linkar via um target C bridging, análogo ao que já é feito com FFmpegKit. (b) reaproveita uma implementação testada pela comunidade; (a) evita introduzir toolchain Rust no build, mas exige portar/validar a lógica de reescrita do RPU manualmente.
4. **Sinalização HLS correta**: a "HLS Authoring Specification for Apple Devices" exige `#EXT-X-STREAM-INF` com `VIDEO-RANGE=PQ` e o codec string `dvh1.05.06`/`dvhe.08.0X` (perfil-dependente) para o dispositivo escolher a variante DV; isso é responsabilidade do gerador de playlist do remuxer (fora do escopo deste doc, mas o dado de perfil/nível que preenche o codec string vem do mesmo `DOVIDecoderConfigurationRecord` já parseado).

Uma vez isso no ar, a "dynamic metadata" em si — a curva de tone-mapping por frame — é aplicada inteiramente pelo VideoToolbox dentro do `AVSampleBufferDisplayLayer`/`AVPlayerLayer` nativo; **nenhum código de tone-mapping precisa existir no KSPlayer**. O trabalho real desta feature é inteiramente de *sinalização/remux correto*, não de renderização.

### Fase 0 (correção barata, no pipeline que já existe hoje — KSMEPlayer/Metal)

Enquanto a Fase 1 não existe, todo MKV com Dolby Vision cai no pipeline atual (`FFmpegDecode` → `VideoSwresample` → `MetalPlayView`), que hoje trata `.dolbyVision` como um caso monolítico e **muito provavelmente é a causa raiz de bugs de cor já relatados no upstream** (issues #771 "lots of purple" e #348 "green and pink tint", ambos em `dvhe.05.06` = perfil 5): perfil 5 usa espaço de cor **IPT-PQc2** para a base layer (não YCbCr Rec.2020 padrão), e o shader que faz essa conversão (`displayYCCTexture`, `Shaders.metal:83-103`, IPT→LMS→RGB) **existe mas não é chamado por nenhum pipeline Swift** (confirmado em `docs/06-render-de-v-deo-e-hdr.md`). Sem essa conversão, o pipeline atual interpreta os samples de um P5 com a matriz YCbCr Rec.2020 padrão (`PlayerDefines.swift:129-136`) — o que produz exatamente o tipo de artefato verde/roxo relatado. Corrigir isso (S/M, dias) é bug fix de correção estática de cor, **não** implementação de dynamic metadata, mas destrava qualquer P5 que chegue nesse pipeline (inclusive antes da Fase 1 existir) de sair com cor visivelmente errada:
1. Ler `assetTrack.dovi?.dv_profile` para diferenciar P5 (`dv_bl_signal_compatibility_id == 0`) de P8 (`== 1/2/4`, base layer já compatível com HDR10/SDR/HLG padrão — por isso P8.1 muitas vezes "funciona por acidente" hoje, ignorando o RPU e mostrando só a base HDR10, o mesmo truque que Infuse fazia historicamente segundo `kingslay/KSPlayer#190`).
2. Para P5: rotear para o pipeline `displayYCCTexture` (habilitar o pipeline no `PlaneDisplayModel`/`DisplayEnum`) em vez do YUV→RGB padrão.
3. Corrigir `DynamicRange.transferFunction` (`PlayerDefines.swift:118-127`), que hoje retorna HLG para **todo** `.dolbyVision` (nunca PQ) — usado em `VideoToolboxDecode.swift:148` (`kVTPixelTransferPropertyKey_DestinationTransferFunction`); baixo impacto prático hoje porque `VideoToolboxDecode` quase nunca roda com os defaults (`asynchronousDecompression = false`), mas é uma inconsistência que qualquer profile-awareness nova deve corrigir junto.
4. Corrigir o bug adjacente já documentado em `FFmpegDecode.swift:113-114` (`display_primaries_b_x` usa `data.display_primaries.2.1.num` em vez de `2.0` — x e y do primário azul saem iguais), que afeta HDR10 estático e por extensão qualquer P8 que dependa do `EDRMetaData` estático.

Este Fase 0 não é "dynamic metadata" strictamente — é a pré-condição de profile-awareness que a investigação já apontou como faltante (`dovi.dv_profile` nunca lido em nenhum branch de código hoje).

## Dependências (de outras features/upgrades)

- **Bloqueante direto**: `proavplayer-mkv-com-dolby-vision-e-atmos-nativos-via-avplaye.md` (status Ausente) — sem o subsistema de remux MKV→HLS local + servidor HTTP + `KSAVPlayer` consumindo a saída, não existe caminho para passthrough nativo de Dolby Vision no StreamHub; a Fase 1 inteira deste roadmap **é** uma fatia daquele subsistema maior.
- **FFmpeg 8.x** (`context/investigation/ffmpeg-version-bundled.md`, hoje 6.1.x via `kingslay/FFmpegKit`): não bloqueia tecnicamente esta feature (as APIs `av_dovi_get_header/mapping/color`, `AV_PKT_DATA_DOVI_CONF`, `AV_FRAME_DATA_DOVI_RPU_BUFFER` já existem desde FFmpeg 5.x/6.x), mas releases mais novas de FFmpeg trazem o bitstream filter `dovi_rpu` (compressão de metadata, `strip`) e `dovi_split` (separação BL/EL de P7) já prontos em C — relevante como alternativa/complemento ao conversor P7→P8 portado de `dovi_tool`, reduzindo o escopo de código próprio a escrever.
- **HDR10 dinâmico** (`context/investigation/hdr10-dynamic-metadata.md`, mesmo padrão de esqueleto morto em `FFmpegDecode.swift:102-105`): não é dependência técnica direta, mas compartilha exatamente a mesma lacuna arquitetural (side data extraído e descartado) — se algum dia a Fase 0 for revisitada para introduzir um tipo `DoviMetaData`/`EDRMetaData` dinâmico, vale desenhar o mesmo tipo para cobrir HDR10+ e HDR Vivid junto, evitando duas soluções paralelas.
- **Infra de remux existente** (`context/investigation/record-video.md`, status Presente) — não bloqueia, mas é a base direta a estender para HLS em vez de recriar do zero.

## Riscos e incógnitas

- **Licenciamento/legalidade do algoritmo real de Dolby Vision**: mesmo com passthrough via AVPlayer, o app não pode (nem precisa) implementar o decodificador Dolby Vision — isso é responsabilidade do VideoToolbox licenciado pela Apple. O risco está inteiramente do lado de **sinalizar corretamente** o stream (atoms/codec strings) para que o SO reconheça e ative esse caminho; sinalização incorreta não trava, mas silenciosamente cai para HDR10/SDR sem aviso (mesma classe de bug dos issues #771/#348).
- **P7 é uma conversão com perda**: descartar a EL (mode 2) joga fora a faixa dinâmica extra do FEL/MEL — o resultado é Dolby Vision profile 8.1 "genuíno" (ainda com RPU dinâmico real, ainda decodificado nativamente), mas não é bit-exato ao profile 7 original. É a mesma perda que toda a indústria de streaming aceita (é como Blu-rays UHD com P7 chegam a serviços de streaming, que entregam P8.1). Não há alternativa nativa no ecossistema Apple.
- **Não existe biblioteca C "oficial" mantida pela Apple ou pela Dolby para essa conversão** — depender de `dovi_tool`/`libdovi` (projeto de terceiro, ainda que MIT e amplamente usado pela comunidade de remux) introduz risco de manutenção: mudanças na spec de Dolby Vision (novas versões de RPU, novos perfis) exigem acompanhar releases upstream do `quietvoid/dovi_tool`, projeto hobby sem SLA.
- **Ambiente de build tvOS/Rust**: se a rota (b) (vendorizar `libdovi`) for escolhida, adiciona um toolchain Rust (`cross`/`cargo-lipo` ou similar) ao pipeline de build do Xcode, algo inédito neste repo hoje (100% Swift/C/Objective-C shim) — risco de fragilidade de CI/build, mitigável escolhendo a rota (a) (porta manual da lógica de mode 2, mais simples: são poucas dezenas de linhas de transformação de campos do RPU, não um decodificador completo).
- **Perfil 7 "single layer" é conceito da comunidade, não da spec Dolby**: o nome da feature usa "P7 single-layer" no sentido de "P7 convertido para rodar como single-layer (8.1)", não um modo P7 nativo de camada única — importante alinhar expectativa com o dono do produto para não gerar confusão sobre o que "suportar P7" significa de fato.
- **Sem amostras de teste no repo**: toda a validação de profile-awareness (P5 vs P7 vs P8, MEL vs FEL) depende de arquivos reais de teste (remuxes 4K com DV, comuns em debrid) que não existem neste checkout — precisa de um conjunto de amostras curado antes de declarar a feature "pronta", dado o histórico de bugs sutis de cor específicos por perfil no próprio upstream.
- **Fase 0 pode mascarar a necessidade da Fase 1**: corrigir a cor estática do P5 no pipeline Metal pode parecer "Dolby Vision funcionando" para quem testar casualmente, mas continua sem dynamic metadata real (RPU nunca aplicado, só a cor de base corrigida) — importante não deixar essa correção barata ser confundida com a entrega da feature em si nos relatórios de progresso.

## Resultado da execução (2026-07-25) — [[dv-nativo]] entregue (código)

Seção adicionada na baixa da task; a pesquisa acima fica como estava. Detalhe completo em [../exec/agora-resultado-2026-07-25.md](../exec/agora-resultado-2026-07-25.md).

**Passthrough P5/P8.1: zero linha de código.** O reconhecimento contra o source do FFmpeg n8.1.2 mostrou que o `movenc` escreve `dvcC`/`dvvC` sob exatamente três condições, todas já satisfeitas desde o [[proavplayer]]: `track->mode == MODE_MP4` (muxer `mp4`), presença de `AV_PKT_DATA_DOVI_CONF` no `coded_side_data` do codecpar de **saída** (propagado por `avcodec_parameters_copy`) e `strict_std_compliance <= FF_COMPLIANCE_UNOFFICIAL` (o remux usa `-2`). O `codec_tag` `dvh1` **não** participa dessa decisão. Ou seja: a fase 1 da pesquisa já estava entregue sem que se soubesse — o que falta é validação de hardware.

**Correção factual importante para o aceite:** o nome da box depende do perfil — `dv_profile > 7` gera **`dvvC`**, não `dvcC`. Como a saída convertida é perfil 8, qualquer inspeção (`mp4box -diso init.mp4`) tem que procurar `dvvC`. Procurar `dvcC` dá falso negativo.

**P7 → P8.1 entregue** via `DOVIPacketRewriter.swift` (novo): walker de NALs length-prefixed (length size lido do byte 21 do `hvcC`), **drop do NAL type 63** (enhancement layer) e conversão do NAL type 62 (RPU) com `dovi_parse_unspec62_nalu` → `dovi_convert_rpu_with_mode(_, 2)` → `dovi_write_unspec62_nalu` do **Libdovi 3.3.2 já vendorizado**. O registro DOVI do codecpar de saída é sobrescrito com `dv_profile=8`, `dv_bl_signal_compatibility_id=1`, `el_present_flag=0`.

**O risco "L→XL" da pesquisa não se materializou:** o Libdovi **cuida sozinho** do emulation prevention e recomputa o CRC32 no `write`, e o buffer devolvido já vem com o header `0x7C01` — não é preciso reserializar bitstream à mão. A dificuldade real ficou no walker/ownership, não na criptaritmética do RPU.

**Limites descobertos:**
- P7 vindo de **MPEG-TS** (extradata Annex-B) é recusado por design: nesse container os packets não são length-prefixed (o próprio `movenc` os converte depois), então o walker não se aplica.
- P7 **dual-track** (RPU numa trilha EL que o remux não mapeia) sairia anunciado como DV 8.1 sem metadata nenhuma — daí a guarda que falha a sessão se nenhuma RPU for convertida até o primeiro fragmento. Nunca confrontado com amostra real.
- Foi usado o **mode 2** (curvas luma/chroma em no-op, padrão `dovi_tool -m 2`); o **mode 4** preserva o mapping e é a alternativa se a validação de FEL mostrar desvio de cor.
- Não corrigível daqui: com sample entry `dvh1`, o `movenc` escreve `hvcC` com `array_completeness = 0` (ele decide esse bit só por `tag == 'hvc1'`). É não-conformidade formal com a ISO 14496-15; impacto no AVFoundation desconhecido.
